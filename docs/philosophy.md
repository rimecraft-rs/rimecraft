# philosophy

The following essences are principles for development, but not instructions for detailed work.
Latter ones are prescribed in other documentations.

## Architecture

rimecraft is a re-implementation of Minecraft in Rust, with many characteristics that is not part of vanilla Minecraft.
This does not mean it will be different on the contents, but architecture-wise.

Minecraft itself is a large running system, not a simple demo generated by an agent in ten minutes. One should treat its
architectural design with care.
Vanilla Minecraft (or Java Edition, to be clear) has a extremely bloated and coherent architecture which one cannot
simply refactor part of it without touching the whole picture, whose mods usually use mixins to change the bytecode in
their own favor while creating more chaos within the running system.
rimecraft is all about removing those coherency from Minecraft with advanced architectures.
This means it should be more like a framework rather than a game, so developers shall do their work as if they are creating
a framework but not a game which just runs.

Most coherency comes from mutual and hard dependencies. For example, `World` depends on `worldgen` and `BlockEntity`,
while the latter ones depend on `World` as well. But what if one just want to view/play a pre-created world without
generating more chunks or he/she just want to get rid of block entities?
These should always be an option, and should not be a feature provided by `World`, as they are only subsystems that exist
in vanilla Minecraft but nothing more special. So the `World` system should always provide capabilities to adopt all sorts of
subsystems. That is, a system should passively accept a subsystem as a part of it instead of actively adopting it.
This could give people more choices and make rimecraft free to construct, and there will be many ways to assemble a running
system which looks, and behaves like Minecraft.

This level of decoherency and extensibility is difficult to reach, though, especially with Rust's statically typed type system.
One still need to balance between safety, simplicity, performance costs and extensibility. Most of the time you may just want
to clone vanilla's micro-architectural design.

## Performance

Another problem of vanilla Minecraft is about performance. It is mostly caused by JVM but in many cases it is caused by design
as well. During development of rimecraft one should be careful of performance, like reducing heap allocations when possible.
Sometimes this may affect architectural design, so don't think all of these could be improved after everything is done.

## Compatibility with Vanilla

As rimecraft is still a Minecraft implementation, external compatibility with vanilla should always be noted.
To reach compatibility of external behavior, we shall treat vanilla as the reference specification but not an
architectural template. Under current architecture there are many ways to assemble a running system, but there should always
exist a particular pattern that resembles vanilla Minecraft.

## Usage of LLM

LLM could be used for boosting up development progress, but with following constraints:

- If you use LLMs for code generation, it should generate in a way that is same as how you would do it by your own. Do not let LLMs to dictate your code.
- Code generated by LLMs should be able to be distinguished between human code.
- Do not use them to generate a wall of slop.

So after all, LLMs take part in the process pretty much like a compiler, not a developer, so it won't use much of its intelligence.
If you find your model's intelligence and creativity is not like what you expect, maybe you used it wrong.
